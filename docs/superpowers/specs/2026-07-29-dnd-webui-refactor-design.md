# DND Web UI 全面重构设计

## 1. 背景与目标

当前前端已经包含房间首页、玩家工作台和管理员控制台，并具备 `DashboardShell`、React Router、feature 目录和设计 token。但视觉规则、全局 CSS 和页面信息层级仍存在历史样式并存、组件边界不完全统一、移动端导航不够明确等问题。

本次重构目标是在不改变后端 API、数据结构和业务行为的前提下，建立一套一致的暖色浅色 Web UI：

- 首页、玩家页、管理员页使用同一套视觉语言。
- 桌面端保留三栏工作台，但明确主任务与辅助信息层级。
- 移动端使用底部一级导航，辅助信息转为抽屉或底部 sheet。
- 玩家页突出剧情日志与行动输入。
- 管理员页突出回合推进与待处理事项。
- 优化响应式、触控、键盘访问、错误反馈和空状态。
- 允许调整信息分组、导航名称和局部 UI 文案，但不改变业务契约。

## 2. 已确认的设计决策

### 2.1 视觉方向

采用 **A · 叙事工作台**：

- 温暖纸张感的浅色背景和内容表面。
- 衬线字体用于标题，无衬线字体用于正文和控件。
- 陶土珊瑚色作为主强调色。
- 低饱和青绿色和琥珀色作为辅助语义色。
- 正文使用深棕黑，避免低对比灰色。
- 第一阶段只做高质量浅色主题，不加入暗色模式或主题切换。
- 不使用 emoji 作为结构性图标，统一使用 `lucide-react`。

### 2.2 范围边界

包含：

- 首页、玩家工作台、管理员控制台的视觉和交互重构。
- 设计 token、共享 UI 组件、响应式 shell 和移动端导航。
- 信息分组、导航命名和局部 UI 文案优化。
- 加载态、错误态、空状态、成功反馈和危险操作确认。
- 可访问性、触控尺寸和 reduced-motion 支持。

不包含：

- 后端 API、数据库结构、SSE 协议和业务状态机变更。
- 新增业务能力或改变现有请求参数、返回值。
- 暗色模式。
- 地图、战斗可视化、语音或其他与 UI 重构无关的功能。

## 3. 总体架构

### 3.1 数据流边界

继续使用现有 React Router 和页面级状态：

```text
页面容器
  ├── 调用现有 API
  ├── 保存页面级状态
  └── 将状态和回调传给 feature 组件
        └── feature 组件负责领域展示与交互编排
              └── 共享 UI 组件负责视觉和通用交互反馈
```

约束：

- `HomePage` 继续负责房间创建、加载列表和删除房间。
- `PlayerPage` 继续负责玩家状态刷新、SSE 订阅、行动提交和交互回应。
- `AdminPage` 继续负责房间刷新、玩家管理和角色审核。
- feature 组件不直接引入 API。
- 共享 UI 组件不依赖领域类型，避免 UI 层和业务层耦合。
- 不改变现有 API 请求参数、响应结构和业务状态机。

### 3.2 自适应工作台

保留 `DashboardShell` 的职责，但演进为响应式应用外壳。

桌面端：

- 顶栏跨全宽，显示产品、房间、当前状态和辅助操作。
- 左侧为一级导航与少量上下文快览。
- 中间为当前页面唯一主任务。
- 右侧为角色、队伍、审核、待办和即时状态等辅助信息。
- 允许拖拽调整左右栏宽度，但降低手柄的视觉干扰。
- 避免三列同时出现多个同等权重的标题和主 CTA。

移动端：

- 顶栏显示房间、状态和更多操作。
- 一级导航收敛为底部主导航。
- 右侧栏转为状态抽屉、底部 sheet 或“更多”页面。
- 当前主任务优先占据首屏。
- 固定底部导航预留安全区域和滚动内边距。
- 尽量收敛为单一主滚动区，避免嵌套滚动干扰。

## 4. 共享组件设计

在现有 `client/src/components/ui` 与布局组件基础上，建立面向产品语义的共享组件：

- `AppShell`：桌面三栏、移动底部导航和辅助面板切换；由 `DashboardShell` 演进。
- `PageHeader`：页面标题、说明、状态和主操作。
- `SectionHeader`：内容区标题、辅助说明和次级操作。
- `StatusBadge`：回合、审核、连接、错误和成功等状态。
- `FeedbackBanner`：错误、成功、警告和处理中反馈。
- `EmptyState`：空列表、未创建角色、暂无日志和无待办等场景。
- `ActionButton`：统一加载态、禁用态、危险操作和图标对齐。
- `ResponsiveNav`：桌面侧栏与移动底部导航共用一份导航定义。
- `ContextPanel`：统一右侧状态面板和移动端抽屉内容。

组件职责边界：

- 共享组件不调用 API。
- 共享组件通过 props 接收内容、状态和回调。
- feature 组件负责领域数据的展示编排。
- 页面容器负责 API、页面级状态和刷新策略。

## 5. 页面信息架构

### 5.1 首页

```text
首页
├── 品牌与产品说明
├── 创建房间主卡
│   ├── 房间名称
│   ├── 预期玩家人数
│   ├── 简短规则说明
│   └── 创建房间 CTA
└── 已有房间
    ├── 房间状态摘要
    ├── 进入房间
    └── 删除
```

设计要求：

- 创建表单成为唯一主视觉和主 CTA。
- 字段提供明确 label、帮助文案和就地验证。
- 房间列表使用状态徽标、人数进度和清晰时间信息。
- 删除采用危险样式、确认提示和删除中状态。
- 空列表提供创建第一个房间的引导。

### 5.2 玩家工作台

继续使用现有四个 feature：

- `PlayerStoryTab`
- `PlayerCharacterTab`
- `PlayerBackpackTab`
- `PlayerDmTab`

导航由同一份定义驱动桌面侧栏和移动底部导航。

剧情页主轴：

```text
玩家 / 剧情
├── 房间、玩家和回合上下文
├── 公开/私密日志切换
├── 剧情日志阅读区
├── 待回应交互卡
└── 行动输入区
    ├── 行动类型
    ├── 建议行动
    ├── 文本输入
    └── 提交状态
```

设计要求：

- 剧情日志是主内容，不再只是普通卡片列表。
- 行动输入固定在内容底部附近，但不遮挡日志。
- 待回应交互使用高优先级提示，但不覆盖整个页面。
- 角色状态提炼为少量关键指标，详细内容放入人物卡。
- 提交成功、等待 DM、失败和处理中均在行动区就地反馈。

### 5.3 管理员工作台

保留五个功能区域，但按任务导向重新命名和排序：

1. 跑团
2. 待处理
3. 战役资料
4. AI 主持
5. 日志与设置

“待处理”作为跑团页顶部的聚合提示，不要求新增后端页面或 API。它聚合：

- 待审核角色
- 待回应交互
- AI 失败
- 需要管理员关注的房间状态

跑团页优先级：

```text
回合概览 → 待处理事项 → 玩家行动 → 推进回合 → 结果反馈
```

管理员右侧上下文面板展示玩家状态、角色审核、资源变更、战斗态势和玩家链接。

## 6. 移动端交互

- 使用底部一级导航替代桌面侧栏。
- 玩家默认导航为剧情、人物卡、背包、DM 助手；其他状态收纳到辅助入口。
- 管理员导航保持任务导向，必要时使用横向可滚动或“更多”入口，但不与底部导航重复嵌套。
- 右侧上下文信息使用抽屉或底部 sheet。
- 关闭抽屉后恢复原滚动位置和当前 tab。
- 固定元素为内容提供足够底部间距，并考虑安全区域。

## 7. 状态、错误与反馈

### 页面级错误

用于房间或玩家状态无法加载：

- 显示明确标题和原因。
- 提供重新加载。
- 提供返回首页或离开当前页面路径。
- 使用 `role="alert"` 或 `aria-live`。

### 操作级错误

用于创建房间、提交行动、审核角色和处理回合：

- 错误显示在对应操作附近。
- 保留用户已输入内容。
- 按钮进入加载态并禁止重复提交。
- 文案说明原因和恢复方式。

### 空状态

每个空状态都应说明当前状态、下一步和可用 CTA，避免只显示低对比的“暂无数据”。

### 危险操作

删除房间等不可逆操作使用危险样式、确认对话框和处理中状态。若后续业务允许，保留可撤销反馈的位置。

## 8. 动效与可访问性

动效：

- 按钮和控件反馈为 `150–200ms`。
- 抽屉和面板进入为 `200–300ms`。
- 内容更新使用轻量淡入或位移，避免布局跳动。
- 不动画化宽高，优先使用 transform 和 opacity。
- `prefers-reduced-motion: reduce` 时关闭非必要动效。

可访问性：

- 页面标题层级连续。
- 表单使用显式 `label`。
- 图标按钮提供 `aria-label`。
- 当前导航提供 `aria-current` 或等价语义。
- Tab、抽屉和弹层支持键盘操作。
- 焦点不会被固定导航或 sheet 遮挡。
- 状态不只依赖颜色，同时提供文字或图标。
- 正文和次要文本满足可读对比度。
- 交互目标至少 `44px`。
- 日志自动滚动不强制打断用户阅读。

## 9. 测试与验收

### 自动化测试

- 首页：创建房间、空状态、加载态、删除确认。
- 玩家页：默认剧情 tab、行动提交、待回应交互和错误反馈。
- 管理员页：待处理聚合区、回合操作和状态徽标。
- 响应式导航：桌面侧栏与移动底部导航共享导航状态。
- 共享组件：按钮加载态、反馈横幅、空状态和抽屉关闭行为。

### 手动验证

- 375px 手机宽度。
- 平板宽度。
- 桌面三栏。
- 横屏。
- 键盘 Tab 顺序和焦点可见性。
- `prefers-reduced-motion`。
- 长文本、长房间名、长玩家名和错误信息。
- 创建房间、生成玩家、提交行动、推进回合和查看日志的完整流程。
- 确认现有 API 操作和信息隔离行为没有回归。

### 成功标准

- 三个主要页面共享一致的暖色浅色设计系统。
- 玩家打开页面后首先看到剧情和当前行动，而不是辅助信息。
- 管理员能够在跑团页顶部快速发现并处理待办事项。
- 手机端可以通过底部导航访问所有一级区域，且内容不会被固定元素遮挡。
- 页面在加载、错误、空状态和提交过程中都有清晰反馈。
- 键盘和屏幕阅读器可以完成主要导航与表单操作。
- `client` 类型检查、现有测试和构建保持通过。
- 后端 API、业务逻辑、数据结构和信息隔离契约保持不变。

## 10. 实施顺序

1. 重整设计 token、全局基础样式和可访问性基础。
2. 将 `DashboardShell` 演进为响应式 `AppShell`，建立移动底部导航和辅助面板机制。
3. 创建共享语义组件并迁移现有通用 UI。
4. 重构首页视觉和信息层级。
5. 重构玩家工作台，先完成剧情页，再迁移人物卡、背包和 DM 助手的外层布局。
6. 重构管理员工作台，先完成跑团页与待处理聚合，再迁移其他 tab。
7. 清理旧 CSS、兼容别名和重复规则。
8. 执行自动化测试、类型检查、构建和响应式手动验收。

## 11. 不变的内容

- API 路径和请求/响应契约。
- SSE 房间更新机制。
- 玩家信息隔离规则。
- 角色审核、行动提交、回合推进和交互回应业务流程。
- 现有领域 feature 的核心职责。

# DND AI-DM 多人跑团 MVP 设计

## 目标

制作一个本地运行的 DND 多人跑团游戏 MVP。系统参考 SillyTavern 的角色、世界信息和对话日志体验，但不复制其代码或完整产品结构。创建游戏后，每位玩家获得一个随机长 token 的专属网页链接。玩家页面只显示该玩家的信息、该玩家可见的故事、公开日志和当前回合进度。AI 扮演 DM，在所有玩家提交本轮行动后按提交时间顺序处理行动，并严格隔离玩家之间的私密信息。

## MVP 范围

首版范围：

- 本地 Web 应用。
- React 前端。
- Node.js/TypeScript 后端。
- SQLite 持久化。
- OpenAI-compatible AI provider 首版实现，并保留 provider 抽象。
- 内置公开 SRD/开源规则数据，并支持用户导入本地规则 JSON。
- AI 辅助角色卡创建，同时允许手动编辑和确认。
- 创建者控制台和玩家专属页面。
- 回合制 AI-DM 流程。
- 玩家间交互需要目标玩家确认，同时 AI 可按规则进行裁定。

不在首版范围：

- 公网部署、账号注册、完整权限系统。
- 完整插件市场。
- 地图、棋盘、语音、视频、复杂战斗可视化。
- 内置受版权保护的 D&D 非公开规则内容。

## 架构

### 前端

前端使用 React，提供两个主要页面：

- `/admin/:roomId`：创建者控制台。创建者可以查看完整状态、导入规则数据、管理玩家、查看回合进度、处理待确认交互、查看 AI 错误和调试信息。
- `/player/:token`：玩家专属页面。玩家通过随机长 token 访问，只能加载该玩家可见的信息。

玩家页面采用 SillyTavern 式的体验：角色信息、世界信息、个人故事和对话日志并列呈现。全局日志只展示公开事件、当前轮次、谁已提交行动、还在等待谁，不展示私密行动内容。

### 后端

后端使用 Node.js/TypeScript，提供 REST API 和实时更新通道。实时更新可以使用 WebSocket 或 SSE，具体由实施阶段根据项目复杂度选择。

核心模块：

- `rooms`：房间创建、世界设定、系统提示词和当前状态。
- `players`：玩家、随机长 token、连接状态和提交状态。
- `characters`：5e 角色卡、AI 草案、手动编辑和确认。
- `turns`：回合状态机。
- `logs`：公开、私密、admin 日志。
- `rules`：SRD/开源规则数据和用户导入规则 JSON。
- `ai`：provider 抽象和 OpenAI-compatible 实现。
- `visibility`：玩家可见数据裁剪。

玩家页面请求不能直接读取全量状态或全量日志，必须经过 `visibility` 层裁剪。

### 数据持久化

SQLite 保存房间、玩家链接、角色卡、规则来源、回合、行动、交互请求、日志和 AI 生成记录。数据库保存完整真相，但玩家 API 永远不能返回完整真相。

## 回合流程

1. 房间进入第 N 轮，所有玩家页面显示当前公开场景、自己的私密状态和行动提交表单。
2. 玩家提交本轮行动。后端记录 `submittedAt`，但不立即结算。
3. 所有玩家提交后，系统锁定本轮行动。
4. AI-DM 按 `submittedAt` 从早到晚处理行动。
5. 普通行动由 AI-DM 结合规则、骰点和上下文结算。
6. 涉及玩家对玩家交互时，系统创建待确认交互。目标玩家需要选择回应、同意、反抗或补充动作后，AI-DM 才继续结算。AI 可以按规则裁定结果，但不能替目标玩家决定意图。
7. 全部行动处理完成后，系统生成公开日志条目、每个玩家的私密故事更新、规则或骰点结果，以及下一轮可见状态。

## 信息隔离

系统把完整真相保存在数据库中，但任何玩家端读取和 AI 生成前都必须先构造可见上下文包。

上下文分为三类：

- `publicContext`：全员可见场景、公开日志、公开骰点、当前轮次和提交进度。
- `playerPrivateContext`：该玩家角色卡、私密线索、只属于该玩家的结果和待回应交互。
- `adminContext`：完整行动、完整日志、AI 调试信息和规则导入状态，只能由创建者控制台读取。

对玩家输出时，AI 必须按玩家分别生成私密内容。系统不能先生成一份完整全局文本再隐藏部分，因为这种方式容易通过措辞、因果关系或暗示泄露其他玩家信息。

## 数据模型

核心表：

- `rooms`：房间名称、系统提示词、世界设定、当前轮次、状态。
- `players`：房间 ID、玩家名、随机长 token、连接状态、提交状态。
- `characters`：玩家 ID、5e 角色卡 JSON、AI 生成草案、玩家确认状态。
- `rule_sources`：内置 SRD/开源规则数据和用户导入 JSON 的来源记录。
- `turns`：房间 ID、轮次、状态、开始时间、结束时间。
- `actions`：玩家 ID、轮次、行动文本、提交时间、处理状态。
- `interaction_requests`：发起玩家、目标玩家、交互类型、目标玩家回应、AI 裁定状态。
- `log_entries`：公开、私密、admin 三类日志，带 `visibilityScope` 和关联玩家 ID。
- `ai_generations`：provider、输入上下文摘要、输出、错误、关联轮次，用于调试和复现。

## 主要服务

- `turnEngine`：控制回合状态、收齐行动、按时间顺序处理、生成下一轮。
- `visibilityService`：唯一负责玩家可见数据裁剪。
- `aiContextBuilder`：为公开叙事、单玩家私密叙事和规则裁定构造不同上下文包。
- `aiProvider`：OpenAI-compatible 客户端和统一接口。
- `rulesService`：加载 SRD/开源规则数据和用户导入规则 JSON。
- `diceService`：统一投骰、保存骰点、把结果写入公开或私密日志。
- `characterService`：AI 辅助角色卡生成、手动编辑和确认。

每个服务都应有明确输入输出，避免把数据库读取、AI prompt、规则裁定和可见性裁剪混在同一个模块里。

## AI 行为约束

AI 扮演 DM，但必须遵守以下约束：

- 不能替玩家决定意图、台词、同意、反抗或 PvP 回应。
- 可以做环境反应、NPC 行动、规则裁定、骰点解释和场景推进。
- 必须按玩家行动提交时间顺序处理本轮行动。
- 生成某个玩家的私密内容时，只能看到该玩家授权可见的上下文包。
- 不能泄露其他玩家的私密行动、私密线索、未公开结果，也不能用暗示性措辞泄露。
- 输出先以结构化结果表示，再由后端写入日志。

结构化结果包含：

- `publicLog`
- `privateUpdatesByPlayer`
- `ruleResults`
- `interactionRequests`

## 错误处理

- AI 调用失败：回合进入 `needs_admin_attention`，创建者控制台显示失败原因和可重试按钮。
- 玩家未提交：回合保持等待状态，公开日志只显示等待进度，不自动推进。
- 玩家交互未回应：回合停在待确认状态，目标玩家页面显示回应请求。
- 规则数据缺失：AI 可以用通用 5e/SRD 解释继续叙事，但结果标记为“规则来源缺失”，创建者控制台可查看。
- Token 无效：玩家页返回无权限，不暴露房间或玩家存在性。

## 测试策略

- 单元测试：覆盖 `visibilityService`、`turnEngine`、`diceService`、`aiContextBuilder`。
- 集成测试：覆盖创建房间、生成玩家链接、提交行动、收齐后推进、生成公开和私密日志。
- 隔离测试：验证玩家 A API 不能看到玩家 B 的私密日志、行动文本、隐藏角色字段或 AI 上下文。
- AI mock 测试：用固定 mock provider 验证流程，不依赖真实模型。
- 手动 UI 验证：本地启动后，用一个控制台页和多个玩家页模拟一轮完整流程。

## 成功标准

- 创建者可以创建房间并生成多个玩家专属链接。
- 每位玩家只能通过自己的 token 看到自己的角色卡、私密故事、待回应交互和公开日志。
- 玩家提交行动后，系统等待所有玩家提交才推进回合。
- AI-DM 按提交时间顺序处理行动。
- 玩家间交互会创建目标玩家确认请求，AI 不替目标玩家决定回应。
- 公开日志不会包含玩家私密行动内容。
- 创建者控制台可以查看完整状态、AI 错误和待处理事项。

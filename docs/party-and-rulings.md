# 协作席位与 DM 裁定

工作台创建没有玩家角色的主持席位，最多四个独立玩家角色通过房号加入；旧战役已有的队长玩家保持不变。世界地点、章节、任务与事件是共享状态；角色的生命、装备、法术位、成长与回合预算分别保存。现有单人战役的原角色和凭证继续作为队长席位使用。**新加入席位需先由 DM 审核**，旧存档无审核字段按 legacy approved 保持可用；角色审核、主输入和纠错新字段以 [输入驱动冒险协议](input-driven-adventure.md) 为准。

---

### 在 Unity 中加入队伍

创建房间只需房间名，得到 8 位数字房间号。主持在工作台「联机与房间」页设置共享加入密码（`#/room`），把游戏服务端地址、房间号和密码私下交给其他玩家，不要发送自己的访问凭证。队伍不在战斗中、没有人倒地时，在任何地点都可以加入，后来者由入场句介绍到当前场景（2026-11-22 起；此前冒险开始后须回到剧本标记的安全休息地点，实玩中队伍离开驿站后朋友就进不了房间）。批准另要求没有待投掷；归档与席位容量限制不变。

队员在 Unity 战役大厅使用同一服务端地址，填写 8 位房间号和共享密码，完成完整一级建卡并在复核页采用；不再提供 Fighter / Wizard 预设。加入会创建独立的一级角色，不会复制队长的任务物品或已领取奖励；新席位先为 `pending`，规则建卡成功不等于 DM 已批准，可阅读资料但暂不能参与行动。主持在工作台审核批准或退回；退回后本人补充说明/按需重新建卡再提交。加入响应丢失时使用「恢复原加入请求」；客户端保存原请求和新席位凭证，服务端返回同一个席位。一次性邀请（`/invitations`）是旧版入口，已有未用邀请仍可加入，新流程不再使用。

Unity 不再提供独立「同行伙伴」页面，队伍头像与聊天头像仍可打开对应同伴的只读角色资料（各自 HP/AC、资源及已有规则说明）。单人和多人的空闲客户端都约每 2.5 秒读取共享版本，工作台裁定也会同步；发送行动、保留待确认请求或切换存档时，不应用旧轮询响应。本机存档列表可以保存同一战役的不同席位，切换前先验证所选凭证。

默认服务只监听本机。两台机器连接需要部署者提供 HTTPS 服务入口与网络配置；目前没有公开部署，也没有把单进程服务器包装成公网账户系统。

### 权限与角色状态

下表“队长 / DM”的本人角色行动仅适用于旧有真实角色的主持席位；新无角色主持只能管理。玩家的短休/长休/等待发起已转为DM全队休整，个人生命骰与来源选择仍由本人决定。

| 操作 | 队长 / DM | 队员 |
|---|---|---|
| 读取队伍、世界、事件和已登记资源 | 可以 | 可以 |
| 操作自己的角色、装备、休息、成长 | 可以 | 批准后可以；待审/退回仅阅读或重交 |
| 操作其他角色的生命、法术位或装备 | 不提供任意修改入口 | 不提供 |
| 在自己的战斗回合行动 | 可以 | 批准后可以 |
| 替其他角色结束回合 | 不可以 | 不可以 |
| 推进已有合法路线、调查主线、对话、任务分支与开战 | 可以 | 批准后可以；仍受场景、队伍及原规则限制 |
| 输入自然行动，必要时升级裁定 | 可以 | 批准后可以；不再每句默认交 DM |
| 设置房间密码、撤销队员、处理裁定 | 可以 | 不可以 |

起步队伍最多四个玩家角色。新无角色主持不占角色名额；旧有角色主持仍计入原四人上限。无角色主持只能管理，不能执行本人行动、角色操作或成长；主持本人要游玩也用房号另建玩家席位。撤销后原凭证立即失效，角色和审计记录保留，仍占用席位；不能通过反复加入制造物品。当前没有席位转让或队长转让；退回申请的本人可通过完整Build重交替换角色，已批准角色不能任意重建。战斗中不允许撤销角色，断线玩家需用原凭证恢复并完成自己的回合。旧版未使用邀请可以撤销；单战役最多登记 64 份邀请。

新无角色主持战役的物品后果归实际行动的玩家；主持裁定仍绑定原行动席位，不选第一个玩家代收。旧有角色主持战役保留历史的队长保管规则。完整建卡的起始装备属于该角色，没有自动交易、平分奖励或转移背包。每个角色可独立达到已经完成的灯塔里程碑。

当前由DM发起全队短休/长休/等待，时间统一推进并对已批准有效角色应用恢复；空队伍不能推进时间。生命骰、奥术回想和来源选择由对应玩家自行决定，不替玩家自动消费。合同见[全队休整](client-contract.md#dm-party-rest)。推进其他行动会关闭刚才短休继续花生命骰的窗口以及即时 Tactical Mind 窗口。

### 协作战斗

新玩家流程开战时，先请每位有效席位分别确认；全员确认前不产生先攻或开始战斗，任一成员可以明确取消。确认齐全后将所有有效角色加入同一先攻序列。详见 [按需投掷](contextual-rolls.md)。队长仍使用单位 ID `player`，队员使用自己的席位 ID；`party.selfActorId` 指明客户端身份。服务端只向当前行动席位返回战斗指令。角色卡始终是自己的角色，不能将共享快照中的队长角色临时替换后保存。

每个角色有独立位置、动作、附赠动作、反应与每回合能力限制。巡守沿最短合法路径接近可行动角色，同距离按席位顺序选择；遇到已在触及内的队员会就地攻击，不自动插入玩家反应。巡守的目标策略属于原创遭遇，不是普遍 D&D 规则。

撤退只撤出当前角色。非致命击倒只影响命中的角色，仍保留 1 HP，并记录其 Unconscious、Prone 和掉落武器。只要其他队员仍能行动，遭遇继续；所有人倒下或撤退才结束。胜利也不会自动治疗倒下的队员。结束后，每位受影响角色分别完成短休与起身拾取。队长不能带仍未完成恢复的有效成员直接旅行。

完整一轮经过 6 秒，不按玩家数量或移动请求数重复计算。棋盘显示所有单位及当前角色的资源，单位详情可以滚动。没有自动化的复杂反应、任意法术、PvP 或通用多怪物编队，继续遵守[遭遇战限制](combat.md)。

### 处理待裁定记录

浏览器主持工作台「剧情」页有实际待办时显示提醒，选择后在处理栏打开具体请求。默认只需选择处理方式、填写给玩家的回应并发送一次，不再叠确认弹窗；规则依据与私密补充按需展开。规则依据未填时明确保存为“主持根据当前情境裁定”，不冒充核验过的规则书出处。后端仍校验理由与来源，权限、原请求恢复和版本条件不变。

纯文字回应、已结算棋盘移动不再自动生成第二个后果待办；检定尚未落实后果才继续提醒。已完成记录仍能从剧情消息下“追加剧情变化（可选）”打开原预览流程，不自动补写 none 或改动事实。主持回应、已记录检定与授权可读的私密说明直接显示在剧情中。

- `reject`：记录未获准，不掷骰、不修改角色。
- `narrative`：记录无数值效果的叙事处理，不把文字解释成状态补丁。
- `check`：队长明确选择属性 / 技能检定或豁免、DC 5..30 及正常 / 优势 / 劣势。新工作台先通知原玩家并显示等待投掷，原玩家确认后才掷骰；状态导致的自动失败直接处理，无虚假投掷。技能只适用于属性检定。服务端使用原提交角色的真实数值，并保留记录的 Exhaustion、适用状态和护甲影响。

技能与属性使用 XPHB p14 的常规 Skills 表，已通过 取证脚本 核对。规则允许 DM 在特定情境改用其他属性；本版表单只开放常规组合，DC 5..30 也是本版入口限制，不是声称规则禁止其他 DC 或组合。

检定仅限请求原场景、原角色仍有效、当前及原请求均在战斗外。失能角色的普通属性检定受限；豁免按已记录状态处理，某些力量 / 敏捷豁免可自动失败。旧战斗请求、已换场景请求仍可驳回或记入叙事审计，不能追溯消耗某人的战斗动作。重复处理同一记录会被拒绝，丢包重试同一请求则返回原检定。

叙事 / 检定入口不解释数值补丁。DM 在理由中写「恢复生命」不会改变生命值；工作台已移除通用角色调整表单，不能声称发送文字就结算了 HP、状态、资源或物品变化。旧 [角色调整](character-play.md) API 与原请求恢复仍保留。经验、等级、生命上限和剧情事实补丁仍不开放；未自动化的复杂法术仍未被执行。人工选择的 DC 与依据明确归属于 DM，不冒充 AI 或规则引擎已经核实的书本结论。裁定可附 `privateText`（≤1000），只给该行动者与主持，见 [contracts.md「私密正文」](../.trellis/spec/contracts.md)。

### HTTP 与持久化

实现见 [PartyService](../server/DiceRealm.Server/Application/PartyService.cs)、[PartyEngine](../server/DiceRealm.Server/Domain/PartyEngine.cs) 和 [RulingEngine](../server/DiceRealm.Server/Domain/RulingEngine.cs)。这些管理命令绕过 AI，与版本、事件和幂等凭据一同提交。

- `POST /api/v1/rooms`：创建房间，`{name}`。
- `POST /api/v1/rooms/join`：无需席位令牌，`{roomNumber,password,requestId,accessToken,build}`；限流，完整构筑按服务端目录检查，访问令牌由加入客户端提前生成并持久保存。
- `POST /api/v1/campaigns/{id}/invitations`（旧版）：队长令牌，`{requestId,expectedVersion,inviteToken}`。
- `POST /api/v1/campaigns/{id}/join`（旧版邀请加入）：无需已有席位令牌，`{requestId,inviteToken,accessToken,characterName,build}`，完整构筑按服务端目录再次检查。两份 capability 必须是独立随机 32 字节的 64 位十六进制字符串；访问令牌由加入客户端提前生成并持久保存。
- `POST /api/v1/campaigns/{id}/seats/revoke`：队长令牌，`{requestId,expectedVersion,actorId}`。
- `POST /api/v1/campaigns/{id}/invitations/revoke`：队长令牌，`{requestId,expectedVersion,inviteId}`。
- `POST /api/v1/campaigns/{id}/rulings/respond`：当前工作台使用的按需投掷入口；旧 `/rulings/resolve` 保留已发请求兼容。队长令牌，`{requestId,expectedVersion,rulingId,outcome,rationale,ruleSource,ability,skill,dc,mode}`。无检定时 `ability/skill` 为空、`dc=0`、`mode=normal`。

加入返回 `CreatedCampaign`；其他命令返回 `ActionResponse`。快照 `character` 是当前认证席位的角色，新无角色主持为 null（同时 `party.isHost=true`），`party` 包含 `selfActorId,isHost,members,invitations,canInvite`。成员包含 `id,role,revoked,character`，邀请摘要没有凭证或哈希。`GameEvent.actorId` 记录行动者，待裁定记录额外保存提交人和处理人。

服务器只持久化 capability 哈希。普通行动与管理命令的幂等键按席位隔离；同一 UUID 不会重放另一位玩家的行动。Unity 待确认文件也按服务端、战役和 capability 派生键隔离，只有已认证队长能接管旧单人客户端的待确认文件。管理命令保存原 endpoint 与 JSON，不能把裁定重试错发到普通行动路由。

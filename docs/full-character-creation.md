# 完整一级建卡流程

战役由工作台创建，玩家只在 Unity 客户端使用固定房间号和共享密码完整建卡后加入。工作台不提供建卡或角色预设，新创建得到没有玩家角色的主持连接；主持本人要游玩也使用房间加入另建玩家席位。加入流程见[房间协议](room-onboarding.md)。

玩家端已改为网页 `/play/`（Unity 客户端不再新增界面）。加入房间先到「创建角色」：按玩法说明选职业，可选种族，起名字就能加入。背景、属性、技能、语言、专长、法术、装备方案和穿戴由页面按职业填好推荐值（`src/play/quick-build.js`），右栏显示服务端检查后的生命值、护甲等级、武器、法术和技能。「详细调整」在同一构筑上打开八步建卡（职业、起源、属性、选择、法术、装备、人物细节和复核），可改任意一项，返回后仍可直接加入。

仍然只有完整构筑能加入：推荐值只是页面替玩家先点好的选项，提交的是同一份完整构筑，服务端照常逐项检查；没有战士/法师模板（`templateId`）或旧简化建卡旁路。规则计算由服务端完成。下文「使用流程」「草稿与依赖」中的 Unity 页面描述是旧客户端记录；八步的规则与依赖清理在网页上相同。

这是 XPHB 2024 一级单职业建卡，不代表全部职业能力已能自动战斗。已有 Fighter / Wizard 角色、旧存档和已接受请求回执继续可用；不能再用预设或旧 `creation` 新建或替换角色。

### 使用流程

1. 主持在工作台创建房间后设定剧本，在「联机与房间」开启共享密码加入。玩家在 Unity「冒险 → 加入房间」填写房间号和密码，打开「完整建卡 / 续写草稿」。
2. 选择职业、物种和背景。目录覆盖 XPHB 的十二个基础职业、十个物种和十六个背景。没有用灰色占位选项冒充可创建职业。
3. 在属性页用 27 点购分配基础值（首次进入按职业主属性给可编辑的推荐起步，也可「清除」回 8 或「使用推荐」），并在同页勾选背景加值。
4. 按来源选择技能、语言、工具、体型、血统、起源专长及职业分支。多选组显示已选数量，单选可直接替换；已满多选需先取消原项。
5. 完成职业与来源法术。法师先记录六个法术书条目，再从书中准备四个；删去书中条目会立即取消对应准备状态。非施法职业仍可能有物种或专长法术选择。
6. 分别选择职业和背景装备方案，完成包内工具或乐器选择，按目录价格购置物品，并明确准备护甲、盾或武器。持有护甲不等于穿戴；未准备时使用无甲规则。商店支持名称筛选和分页。
7. 填写姓名、称谓、外貌、性格、经历和阵营。只有姓名必填；人物文字不产生额外熟练、装备或法术，也不提交给模型。
8. 在复核页查看服务端返回的数值、取得记录、提醒和缺失项。点击问题可返回相应步骤。「采用」返回房间加入页，仍需明确提交加入；新角色进入 `pending`，由工作台批准或退回，规则合法不等于已经批准。

未采用当前有效完整构筑时，加入始终禁用。关闭建卡只保存草稿，不会采用；重新打开编辑会使外层旧采用失效，必须重新检查并采用。采用后的姓名只读，修改需回建卡窗口；不存在恢复预设的旁路。

### 草稿与依赖

草稿保存在本机 `Application.persistentDataPath/character-build-draft.json`。保存、切换步骤和关闭窗口都会尝试原子写入；未完成选择同样可以保存。重新打开或重启会恢复最近草稿和所在步骤，并重新请求检查，不从磁盘恢复“已验证”状态。

职业变更清除职业技能、法术、装备方案、购物清单和基础属性分配；物种变更清除物种来源选择；背景变更清除背景加值、其来源选择、背景装备与购物清单。来源分支按服务端的 `dependsOn` 递归清理后续选择。姓名和无关来源不会被全部重置。已访问、需复核、缺失项与当前预览是不同状态。

每次修改会立即作废旧预览。只有当前编辑版本和当前窗口的响应可以更新选择组或启用采用；网络错误、关闭、销毁及迟到响应不能恢复旧预览。保存失败会保留窗口输入并阻止采用。损坏或规则版本不匹配的草稿禁止覆盖，用户可明确选择先保存原文件副本再重新开始。

草稿不是服务器角色申请，也不含战役凭证。当前只维护一份本机续写草稿，没有多角色草稿库或云同步；DM 审核在加入后的服务端角色申请上进行。加入请求另有持久重放机制，完整 `build` 与原加入请求一起保留，断线后不会换成另一份构筑重试。已被旧服务接受的预设加入仍按原请求恢复，尚未接受的旧请求明确拒绝，不自动转换。

### 服务端权威与规则边界

[BuildEvaluator](../server/DiceRealm.Server/Domain/Creation/BuildEvaluator.cs) 负责选择合法性、背景加值、点购费用、技能与专精、装备预算、初始穿戴、生命值、护甲、全部技能和豁免数值、速度与来源施法属性。Unity 只编辑输入并展示结果；金币编辑提示来自目录，最终预算以服务端检查为准。检查接口不写战役、不掷骰、不调用模型，最终创建和加入会重新验证。

[BuildChoices](../server/DiceRealm.Server/Domain/Creation/BuildChoices.cs) 返回有稳定来源键的选择组。Human 的额外起源专长、Magic Initiate 的列表和施法属性、血统、圣职、武器精通、战斗风格、盗贼专精等都保留具体选择，不隐藏成固定预设。重复获得同一技能熟练只计一次熟练加值，并显示提醒，不自动叠加成专精或赠送替代熟练。

目录从显式 `dnd2024` 的本地 stdio MCP 结果及同一固定 provider revision 的补充数据生成。取证脚本是 verify_full_creation_rules.py，生成器是 build_creation_catalog.py，运行时只嵌入 [精简目录](../server/DiceRealm.Server/Domain/Creation/creation-catalog.json)。完整规则原文留在忽略的本机取证目录，不随游戏分发。没有在查询缺失时回退到 2014 数据。

来源处理保留了可核对的差异：Cleric 装备 A 使用正文的 7 GP，未沿用原始结构字段中的错误值；Wizard 的起始法术书按 XPHB p165 职业取得记录，装备 A 不重复赠送，金币方案也不借用 2014 的法术书价格；无已核对整铜币价格的物品不能在商店购买。旧代码把持有护甲视为穿戴的问题没有照搬。

[BuildRuntime](../server/DiceRealm.Server/Domain/Creation/BuildRuntime.cs) 保持角色实际装备后的 AC、速度、隐匿劣势和生命骰类型。新构筑不会被当成 Fighter 代算。固定遭遇自动战斗仍只接受已实现的能力与装备组合；其他构筑可以创建、保存、探索和提交主持裁定，但不能直接开始该自动战斗。角色操作现已支持基础检定与豁免、已持有规则装备换装、来源施法 / 资源消耗和长休后准备替换，主持可预览并保存生命、状态、资源与物品变化，见 [角色使用](character-play.md)。完整法术效果、专长连带行为、反应、双持和负重仍需主持处理。完整建卡角色目前只到一级，不套用旧预设的二级固定成长。

服务端接受标准数组和点购，Unity 属性页只提供点购；随机属性生成、子职、多职业、高等级建卡、全部规则书内容和开放式自动战斗未实现。角色卡保留人物细节、完整取得选择、来源法术的独立攻击 / DC，以及服务端技能和豁免值，不把“已取得”显示成“已施放”。

### 协议与实现

- [客户端协议](client-contract.md#full-level-one-character-build) 说明目录、检查、创建和加入的兼容字段。
- BuildDraftState 管理草稿编辑、依赖清理、导航与响应版本。
- BuildDraftStore 管理本地保存与损坏草稿保护。
- CharacterBuilderPanel 管理窗口、请求和采用；CharacterBuilderSteps 渲染八步内容。界面按 BG3 三段式（左步骤、中面板、右只读摘要）：CharacterBuilderLayout 拥有布局件，CharacterBuilderAbilities 为属性页，CharacterBuilderSpells 为法术页，CharacterBuilderChoices 为来源选择。细则见 [Unity 前端规范](../.trellis/spec/frontend/unity.md)。
- [FullCreationTests](../tests/DiceRealm.Tests/FullCreationTests.cs) 验证职业、物种、背景的笛卡尔组合及独立边界用例。组合测试采用每组合法选择，不宣称穷举了所有法术、专长与装备排列。
- FullCharacterBuilderTests 验证真实 Unity JSON、草稿恢复、晚到响应、保存故障、复核门槛、加入选择及文字布局。

# 复用与可维护性

## 设计标准

1. 先找到行为的所有者，再修改；不要在每个调用者叠补丁。服务端拥有规则，传输边界拥有解码，面板拥有展示与交互。
2. 优先清楚的函数和数据结构。只在外部资源、可替换实现或测试隔离确有需要时引入接口；不为每个 service/repository 再加一层转发。
3. 相同业务含义且必须一起变化的逻辑才共享。两个文案或数值暂时相同，不足以创建通用配置；Unity 和浏览器不强行共用 UI 框架。
4. 新模块按一个可说明的职责命名。避免继续扩大万能工具、全局状态或大协调器；也不要仅为缩短文件拆出相互依赖的碎片。
5. 新的非平凡分支、状态更新和错误处理分行写清楚。服从 [.editorconfig](../../../.editorconfig)，邻近代码只做必要调整，不批量压缩或格式化无关文件。
6. 注释说明约束和原因，不翻译语句。命名表达业务概念；避免只有当前作者理解的缩写。

## 本项目的取舍

- [AiPorts.cs](../../../server/DiceRealm.Server/Application/AiPorts.cs) 的在线/离线适配器和 客户端 Abstractions.cs 的文件/时钟隔离有真实替换需求，适合作为接口边界示例。
- StoryFlowPresentation.cs 把故事展示投影放在无引擎代码中，便于测试；不应在多个面板各自拼接最新事件。
- [GameService.cs](../../../server/DiceRealm.Server/Application/GameService.cs) 和 AdventureApp.cs 目前通过 partial 文件组织较大的协调器。这是现状，不是要求新功能继续塞进去。新增复杂行为优先放到拥有该行为的模块，协调器只连接它。
- 仅发生在一个职责内的简单辅助函数就留在该文件。不要因为「以后可能用到」建立公共框架。

## 改动前后的判断

写下实际行为差异、所属模块、必要文件和不做的部分。局部重构若能明显降低本次风险，可以与行为测试一起做；大范围搬迁、换框架和数据迁移另列范围与回滚方案。

复用前先搜现有语义；批量改动后搜索遗漏的消费者。成功标准是维护者能定位和修改一个行为，且不会无意改变另一个行为，不是抽象层越多越好。
